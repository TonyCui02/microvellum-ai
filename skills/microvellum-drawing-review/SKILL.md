# Drawing review and XML draft

Work from the root of the microvellum-ai checkout. Read `README.md`, `poc/README.md`, and `docs/xml-workflow.md` before beginning; those documents describe dependencies, model fields, commands, and current limitations. Keep the source PDF, catalog, working model, rendered pages, and output in a private job directory outside the checkout. **For PDF input, render every page to PNG before interpreting the drawing. The LLM must inspect the PNG page images and must not read, parse, or visually review the PDF itself.** If any page image is missing, unreadable, or illegible at the rendered resolution, stop and rerender at a suitable DPI or ask for a clearer source; do not fall back to PDF input.

When the user requests a lasting shop rule, use `py scripts/mv.py rules add` or `update`; use `--help` for fields. Clearly distinguish job-only corrections from persistent rules, and resolve ambiguity or conflicts with the user. Do not create shop rules from unverified catalog data. Rules default to `~/.microvellum-ai/rules.json`; `MV_RULEBOOK` or `rules --rulebook PATH` selects a private shared rulebook. At the start of every job run `rules list`. After creating the model run `rules snapshot --model PATH`, then evaluate every enabled rule in `review.rules.evaluations`: set status to `applied`, `not_applicable`, `needs_clarification`, or `cannot_evaluate`; provide a reason and source evidence and affected item IDs. A rule in conflict with drawing evidence or another rule must remain unresolved until the user decides. Do not silently treat an unknown as not applicable. Update the model revision and obtain fresh review approval after changes. Before export re-evaluate when the rulebook or relevant job facts change. Export blocks incomplete or unresolved evaluations; only use `--use-saved-rules` on explicit user instruction to use the earlier snapshot. Rule checks verify records, not the correctness of agent judgment.

1. Obtain the drawing. `scripts/mv.py` uses the bundled Kitchen Library V7.1 catalog by default and verifies its manifest checksum; use it for catalog search, prompt inspection, review and export. Read `data/catalog/manifest.json` and record its fingerprint. Its snapshot's completeness and match to the active installation are unverified; do not invent product identities. Use a different catalog only when the shop supplies one and its provenance is understood. Use SQL CE analysis only if needed and never open a live SDF with a writable exporter.
2. Render every PDF page with `py scripts/mv.py render`. Inspect the resulting PNG images, not the PDF. Inspect the full pages and relevant details visually. Before marking any dimension unknown, search the corresponding plan, front/elevation, section, detail, and notes across all rendered page images for that value; cross-check dimension chains and endpoints between views. Record the views and pages checked and what was found in that dimension's evidence. Only leave it unknown after this search finds no reliable value. Record source evidence, units, uncertainty, and all visible entities in the drawing inventory as described in the review guide. Do not infer missing dimensions as facts or rely on unconfirmed shop defaults.
3. Resolve exact catalog product and group identities and inspect relevant prompts. Present the proposed layout, schedule, assumptions, and unresolved items. Keep material assignments at the selected library and specification-group defaults; do not add per-item material selections. Ask focused questions where ambiguity affects the result. Use the local review page when useful; it is schematic and does not interpret drawings itself.
4. Before asking the user to review the page, render local model views with `py scripts/mv.py model-views MODEL.json --out MODEL-VIEWS-DIR`. Inspect `front.svg`, `top.svg`, and `3d.svg` alongside the source PDF page renders. Browser control is not needed for this comparison. `?` marks dimensions drawn using approximate placeholders; consult the JSON and PNG evidence before accepting those relations. Compare each view to its corresponding drawing view when present; otherwise check consistency with available orthographic evidence and record why a direct comparison was unavailable. Fix discrepancies and repeat. Record all three results in `review.visual_self_check`; any model edit clears the self-check, so rerender and repeat before presenting the revised page.
5. Record actual user review and corrections. Export with `py scripts/mv.py export` only when its validation requirements are met. Inspect the resulting validation report and tell the user which requested details were omitted or remain unverified. If requirements cannot be met, report the blocker rather than fabricating an approved model or XML.
6. Deliver the draft and its validation report for manual evaluation. One specific historical XML was reported successfully imported and checked against its drawing, but this does not establish that new exports produce correct geometry, settings, or manufacturing output. Do not promise production readiness, automate Microvellum, modify factory databases, or generate CNC output.

For deeper investigation, the bundled catalog is SQLite: open `data/catalog/kitchen-library-v7.1.sqlite` with `sqlite3.connect(path.resolve().as_uri() + '?mode=ro', uri=True)`. Its `entities`, `workbooks` and `prompt_names` tables contain indexed data; workbook `payload` values are zlib-compressed JSON. Machine-local relationship targets are redacted, and raw workbooks and source SDF tables outside the index are not bundled. State when an investigation requires evidence the index does not contain.
