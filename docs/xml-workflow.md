# Experimental XML workflow

This is an offline **calibration prototype**, not a production exporter. The user reports that one 13-product draft imported successfully into Microvellum and that its product count, positions, dimensions and settings were checked against the drawing and correct. This is evidence for that specific file, not independent verification of other exports or manufacturing output. The original generated validation report predates the import and does not record it. Its private XML SHA-256 is `143ce303ed8a1a8b2c8a6b38a93e6e9475c77adc04657a2f93af7abee29a84d1`; its source and job files are not distributed. The draft itself omitted several drawing elements, as recorded in its private manifest.

The implemented subset is a named project, locations, specification groups, and individually placed products. It accepts exact product record IDs (so duplicate display names can be explicitly resolved), dimensions, origins, angle, item number, product Comment, and static named prompt values that resolve uniquely in the indexed product workbook. Specification groups may include named Global prompt candidates whose values are checked against the selected indexed Global workbook; these XML fields are documented by sample files but remain uncalibrated. A product can carry a positive integer quantity; it still has one position. Target behavior for quantities greater than one is unverified. It emits no Walls, LinkIDWall or product named `Wall`. Per-item material assignments are not collected or emitted; products inherit whatever defaults are provided by the selected library product and specification group. This workflow does not evaluate effective material defaults. It does not handle full workbook formulas, geometry collision checks, automatic coordinate/unit conversion or target importer behavior. Unknown fields are rejected. The POC drawing exporter requires a complete drawing inventory and a reviewed issue-free model; unresolved entities block output. Do not use for production handoff.

## Prepare

1. Use the bundled analysis catalog to resolve exact products, specification groups, and product prompts. Its completeness and match to the active installation remain unverified; effective workbook formulas and defaults are not calculated.
2. Copy [the model template](../tests/fixtures/xml-model-template.json) outside tracked paths. Fill every field; choose exact names and associated record IDs. Fill `catalog_sha256` with `(Get-FileHash -Algorithm SHA256 data/catalog/kitchen-library-v7.1.sqlite).Hash.ToLower()`. Set `review.status` to `reviewed` only after dimensions, coordinates and assumptions have actually been reviewed. The sample numbers are placeholders. Each product may contain `prompts: [{"name":"...","value":"..."}]`; each name must map uniquely in that workbook. A well-formed value is not evidence that the importer applies it.
3. All dimensions and origin values are decimal **strings**, in the stated `output_units` (`mm` or `in`), already expressed in the hypothetical native XML coordinate system. Angle is also a decimal string. The tool performs no conversion or transformation, and the target interpretation of all these fields remains unknown. The `native_unverified` marker describes that uncertainty; choosing a unit here does not verify it.
4. Run from the workspace root:

```powershell
python src/mv_kitchen/xml_workflow.py validate --model C:/path/reviewed.json --catalog data/catalog/kitchen-library-v7.1.sqlite
python src/mv_kitchen/xml_workflow.py export --model C:/path/reviewed.json --catalog data/catalog/kitchen-library-v7.1.sqlite --experimental --out C:/path/new-calibration-output
```

The output directory must not exist; the command will not overwrite an existing one. Keep private job files outside Git. Export writes `project.xml`, `validation.json`, and a warning README. Validation prints JSON to stdout and returns 0 if implemented static checks pass; failures return 2 and a JSON error on stderr. A successful result is deliberately `insufficient_evidence`, with `target_import_tested: false`, not an import-ready claim. The manifest records model, catalog, source SQLite and XML hashes. Retain the input model alongside it for later comparison.

The checker requires the exact selected record ID/name pair, product type 1 as observed in the root library, matching nonempty product/group library links, and an indexed workbook. Prompt overrides are blocked for an incomplete workbook stream. An incomplete stream without overrides can produce a draft but remains insufficient evidence. The selected record ID resolves catalog duplicates internally; XML still uses the exact product display name, so target importer resolution can remain ambiguous. This is not proof of active configuration ownership or complete workbook/dependency semantics. It does not check whether the group is supported for that product. A separate XML parser compares emitted facts with the normalized model; this is a consistency check, not an importer emulator.

For a previously exported project snapshot, `investigation/sqlce/project_to_model.py` creates a canonical reference JSON from its SQLite analysis copy and exact product/category matches. It distinguishes `Projects.JobNumber` from `Projects.ProjectNumber`; the latter remains in JSON because no verified XML mapping is known. Product comments are joined with `|` from the four observed comment columns; this mapping is based on an example XML and is uncalibrated. It extracts static numeric inputs plus numeric cached values from formula-backed prompt cells when they differ from the selected research-catalog workbook. With `--include-literal-text`, it also includes nonempty literal text prompt candidates. These are candidates, not proven overrides: writing a cached formula result can freeze a calculated value, and neither catalog provenance nor target formula recalculation is established. The report preserves provenance. Unreadable or unsupported candidates and invalid quantities block export. `investigation/sqlce/compare_project_xml.py` independently compares XML against project/location/product rows and these candidate values, checking item coverage, exact names, comments, dimensions, quantities, origins, angle, group/location links and the no-wall rule. These helpers read SQLite analysis copies only, never write SDF, and do not establish importer compatibility or full project-workbook equivalence.

## Calibration and next implementation

Extend the reported successful example with a matched target library/configuration and recorded import results for other representative layouts. Confirm target units, axes, angle and insertion anchors; verify location, group assignment, dimensions, prompt behavior and rendered placement. Record the exact XML hash, build, library/component fingerprints, expected and observed results. Product instance data not represented by this XML contract (including binary workbooks, subassemblies and calculated formulas) must be reported as unmatched rather than treated as included. Products use the selected library and specification-group defaults; those defaults are not evaluated here.

Run the synthetic regression tests with `python -m unittest discover -s tests -v`. The tests use fabricated catalog records and do not test Microvellum itself.
